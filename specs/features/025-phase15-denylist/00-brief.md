# Brief: Phase 15 Denylist Completions

> Closes two remaining Phase 15 items in `PROJECT_PLAN.md`:
> 1. **Full regex denylist support** (currently only substring/prefix/suffix/exact).
> 2. **Clipboard ignore rules by source application** (currently `source_app` is
>    stored on items but never filtered against user rules).

---

## Problem

### 1. Regex denylist
The current `content_pattern_mode` config offers only `substring`, `prefix`,
`suffix`, and `exact`. Users who want flexible matching (e.g. "starts with
`ghp_` or `sk-`, length 30+") cannot express it without writing four
patterns per family. A regex mode removes this limitation and matches user
expectations set by tools like `clipboard-filter` and `pasteguard`.

### 2. Source-app ignore
`PROJECT_PLAN.md` promises "Clipboard ignore rules by source application
(where Wayland allows)". Today the `source_app` column exists on every
clipboard item but no config field consults it. Even though the wlr-data-control
protocol does not currently expose source-app metadata to the daemon (a
compositor limitation — see [`09-decisions.md`](09-decisions.md)), we can:

- Add the `app_denylist` config and the matching logic now (tests in place).
- Wire the daemon to call it on insert when `source_app` is set.
- Ship this as **forward-compatible**: once a compositor does provide
  source-app info, the rule takes effect with no further code changes.

## Goals

- One new `ContentPatternMode::Regex` variant, gated on a workspace-pinned
  `regex` crate, with safe failure on invalid patterns.
- One new `Config::app_denylist: Vec<String>` field with substring/exact
  matching semantics.
- Wire both into the daemon's capture path (text, HTML, files).
- Unit tests covering happy path and adversarial inputs (invalid regex,
  empty strings, Unicode).

## Non-Goals

- Encrypted export/import (separate feature).
- Snippet templates with token replacement (separate feature).
- Per-item hotkeys / paste macros (separate feature).
- OCR pipeline (separate feature).
- Tracking down which compositor protocols actually expose source-app info
  — that's a follow-up research task; this spec only adds the configuration
  surface and matching logic.
